🎮 T1 - 논타겟팅 액션 MMORPG

📆 2026.01 ~ 진행 중 (개인 프로젝트) GitHub corea1836/T1-Server

  • Boost.Asio
  • Protobuf
  • 멀티스레딩

T1은 대량의 플레이어를 수용하면서도 실시간 논타겟팅 전투의 짜릿한 손맛을 살린 MMORPG를 목표로, C++17과 Boost.Asio로 직접 만들고 있는 게임 서버입니다(Unity 클라이언트 연동). 처음부터 완성형 기법을 넣지 않고, 부하 봇과 서버 지표로 문제를 먼저 재현하고 측정한 뒤 가장 단순한 구조로 해결했습니다.

문제 해결

서버→클라이언트 패킷 전송 병목: 쓰기 경로 분리

문제
  • 서버는 1초에 20틱(50ms 간격)을 돕니다. 봇 50/100/200 기준선을 재 보니, 봇 100명부터 서버 틱 시간 p50이 53~56ms로 틱 간격(50ms)을 넘어 데드라인을 절반쯤 놓쳤고, 200명에서는 1초에 4틱만 돌았습니다.
접근
  • 프로파일링해 보니 틱 시간의 97%가 송신이었고, 송신 패킷 수와 쓰기 시스템 콜 수가 거의 같았습니다. 틱을 도는 게임 스레드가 패킷마다 직접 시스템 콜(sendmsg)을 하고 있었습니다.
  • 세션마다 strand(한 세션의 작업을 순서대로 실행하는 직렬화 큐)를 두고, 게임 스레드는 송신 큐에 넣기만 하고 시스템 콜은 네트워크 스레드가 하게 바꿨습니다. 쓰기가 진행되는 동안 쌓인 패킷은 다음 쓰기 한 번에 묶여 나가므로 시스템 콜 횟수 자체도 줄었습니다.
결과
  • 서버 틱 시간 p50이 15ms → 0.33ms로 98% 줄었고(봇 50), 봇 200명에서도 1초에 20틱을 다 돌아 데드라인 초과가 0입니다. 쓰기 1번당 패킷은 1개에서 22~38개로 늘었습니다.
  • 소켓 작업이 strand 하나로 모이면서, close와 쓰기가 겹쳐 서버가 죽던 경쟁도 사라졌습니다. 접속/종료 반복 봇과 TSan으로 120초 돌려 경고 0건, 크래시 없음을 확인했습니다.

접근

문제
  • 서버 권위 이동이라 내 캐릭터가 왕복 지연만큼 늦게 반응합니다. 지연 시뮬레이터로 왕복 300ms를 재현하니 키 입력 후 출발까지 350~383ms가 걸렸습니다.
접근
  • 클라이언트가 서버와 같은 이동 식(방향 × 속도 × dt)으로 먼저 움직이게 해, 서버 권위는 유지한 채 입력한 프레임에 반응하게 했습니다.
  • 패킷에 입력 번호(seq/ack)가 없어 이동 중에는 서버 위치와 비교할 수 없습니다. 그래서 나와 서버가 모두 멈췄을 때만 서버 위치로 보정했고, 패킷은 바꾸지 않았습니다.
결과

  • 멈춘 뒤 살짝 미끄러지는 한계가 남아서, 입력 번호 기반 재시뮬레이션을 다음 단계로 정했습니다.

견고한 주문 시스템 구성

특정 상품에 주문 요청이 몰렸을 때 DB 커넥션 고갈, 독점 문제 해결

문제
  • 특정 상품에 주문이 몰리면, 긴 트랜잭션으로 DB 커넥션이 부족해져 신규 주문 요청들은 request-timeout과 함께 실패했습니다. * 커넥션 설정을 늘려도 더 많은 주문 수행 시 클라이언트 read-timeout과 함께 실패했습니다. * 주문 API 평균 시간: 약 1초 이상 / Connection Pool-Size: 10 → 20 / Connection-Timeout: 30s → 3m
접근
  • DB 커넥션을 얻기 위해 대기하는 요청이 필요한 경우 대기열에 자신의 순서를 기록하고 즉시 요청을 반환해 서버 내부에서 대기하는 요청을 최소화했습니다.
    사용자는 자신의 차례가 왔을 때 DB 커넥션을 획득해 주문을 실행할 수 있기 때문에 커넥션 획득할 수 있도록 했습니다.
    대기열은 Redis의 sorted-set 자료구조를 사용해 주문 중복 제거와 순서를 보장했습니다.
결과
  • 대기열 도입 전 특정 상품에 동시 주문 요청 수가 30개만 넘어도 request-timeout이 발생했지만, 도입 후 동시 주문 요청 수가 500개일 때에도 모든 주문하기 요청을 정상 처리할 수 있었습니다.

순서와 동시성을 보장하는 안전한 주문하기 기능 구현

문제
  • 멀티 스레드 기반의 WAS에서 동시에 주문을 수행하면 요청 수 미만으로 재고가 차감되는 재고 정합성을 보장하지 못하는 동시성 문제가 발생했습니다.
접근
  • UPDATE 쿼리의 배타락을 활용해 재고 정합성을 확보했습니다.
  • 주문 요청의 순서는 앞단의 Redis sorted-set 대기열에서 보장했습니다.
결과
  • 주문 요청 순서를 보장하며 동시성 문제가 발생하지 않는 주문하기 기능을 구현할 수 있었습니다.

신뢰성 있는 결제 시스템 구성

결제 기능 구현

구현 내용

결제 지연으로 주문 이상 건 문제 해결

문제

접근
  • PG사에서 제공하는 결제 완료 상태의 Webhook을 활용해 이중 검증함으로써 결제 내역과 주문 내역을 동기화 했습니다.
