집계와 이상 지출 감지

문제 해결

스펙과 실행 흐름을 코드로 고정

문제
AI는 긴 작업에서 규칙을 잊고, 범위를 넘기고, "다 했다"는 말만으로 끝내 결과를 믿기 어려웠습니다.
접근
  • PRD·ADR 25개·제외 목록으로 요구사항과 금지사항을 고정하고, step마다 실행 가능한 완료 기준(AC)을 명세했습니다.
  • 실행기가 step마다 새 세션을 띄우고, AC 결과로만 완료를 판단하며, 재시도·중단·재개를 코드로 통제합니다.
  • 테스트 없는 구현, 파괴적 명령, 공유 DB 변경은 훅으로 실행 전에 막았습니다.
결과
69 step 중 65개(94%)가 사람 개입 없이 완료되었습니다.

구현과 검증을 다른 모델로 분리

문제
같은 모델이 자기 코드를 검증하면 맹점이 그대로 통과하고, 커밋을 막는 리뷰는 거짓 경보 하나로 작업이 멈춥니다.
접근
  • 리뷰어 3명이 관점별로 검토하고, 지적마다 skeptic 3명이 코드 근거로 반박을 시도합니다.
  • 2/3가 인정한 지적만 커밋을 막고, 판단이 갈린 지적은 사람에게 넘겼습니다.
결과
단위 테스트 2,410개, pgTAP 단언 630개가 통과하고, 테스트와 제품 코드의 비율은 약 2:1입니다.

문제

결과

금액 정합성과 개인 금융 데이터 보호

문제
파싱 오류나 LLM이 만든 숫자는 잘못된 금액으로 이어지고, 카드 이용내역은 민감한 개인 데이터입니다.
접근
  • 금액은 코드로만 계산해 명세서 총액과 원 단위로 대조하고, 겹치는 파일을 올려도 같은 거래는 한 번만 반영합니다.
  • 원본은 AES-256-GCM으로 암호화하고, RLS로 사용자별 데이터를 격리하며, AI에는 가맹점명과 집계만 보냅니다.
결과
금액 오차와 데이터 유출을 테스트로 막는 구조를 만들었습니다.

⏰ Just 10 Minutes

타임딜 서비스인 Just 10 Minutes는 e-commerce 플랫폼에서 다루는 주문, 결제 시스템을 바탕으로 대규모 트래픽이 발생했을 때 마주하는 기술적 문제를 해결하기 위해 고민한 프로젝트입니다. 주요 기능으로 주문, 재고 관리, 포인트 관리, 결제, 대기열 기능 등이 있습니다.

견고한 주문 시스템 구성

특정 상품에 주문 요청이 몰렸을 때 DB 커넥션 고갈, 독점 문제 해결

문제
  • 특정 상품에 주문이 몰리면, 긴 트랜잭션으로 DB 커넥션이 부족해져 신규 주문 요청들은 request-timeout과 함께 실패했습니다. * 커넥션 설정을 늘려도 더 많은 주문 수행 시 클라이언트 read-timeout과 함께 실패했습니다. * 주문 API 평균 시간: 약 1초 이상 / Connection Pool-Size: 10 → 20 / Connection-Timeout: 30s → 3m
접근
  • DB 커넥션을 얻기 위해 대기하는 요청이 필요한 경우 대기열에 자신의 순서를 기록하고 즉시 요청을 반환해 서버 내부에서 대기하는 요청을 최소화했습니다.
    사용자는 자신의 차례가 왔을 때 DB 커넥션을 획득해 주문을 실행할 수 있기 때문에 커넥션 획득할 수 있도록 했습니다.
    대기열은 Redis의 sorted-set 자료구조를 사용해 주문 중복 제거와 순서를 보장했습니다.
결과
  • 대기열 도입 전 특정 상품에 동시 주문 요청 수가 30개만 넘어도 request-timeout이 발생했지만, 도입 후 동시 주문 요청 수가 500개일 때에도 모든 주문하기 요청을 정상 처리할 수 있었습니다.

순서와 동시성을 보장하는 안전한 주문하기 기능 구현

문제
  • 멀티 스레드 기반의 WAS에서 동시에 주문을 수행하면 요청 수 미만으로 재고가 차감되는 재고 정합성을 보장하지 못하는 동시성 문제가 발생했습니다.
접근
  • UPDATE 쿼리의 배타락을 활용해 재고 정합성을 확보했습니다.
  • 주문 요청의 순서는 앞단의 Redis sorted-set 대기열에서 보장했습니다.
결과
  • 주문 요청 순서를 보장하며 동시성 문제가 발생하지 않는 주문하기 기능을 구현할 수 있었습니다.

신뢰성 있는 결제 시스템 구성

결제 기능 구현

구현 내용
  • 사용자에게 결제하기 전 카드 등록을 요청하여 포트원 빌링 키 발급 API를 연동하여 빌링 키를 발급받았습니다. * 빌링 키란? : 고객의 카드 번호, 유효기간, CVC 등 결제 정보를 암호화한 키 값
  • 기존 주문 프로세스의 최종 단계에 포트원 빌링 키 결제 API를 연동하여 발급한 빌링 키를 통해 결제를 수행하는 프로세스를 추가하였습니다.

결제 지연으로 주문 이상 건 문제 해결

문제
  • 결제는 정상 처리되었지만, 주문이 정상 처리되지 않아 금전적 손실을 유발하는 심각한 문제 발생 여지가 있습니다. * PG사 지연으로 주문 API time-out, 결제 요청 성공 후 내부 서비스 문제로 주문 API 실패 등
접근
  • PG사에서 제공하는 결제 완료 상태의 Webhook을 활용해 이중 검증함으로써 결제 내역과 주문 내역을 동기화 했습니다.
  • 결제 내역과 주문 내역의 상태가 일치하지 않는 건은 시스템 운영자에게 슬랙 알림을 주도록 구현했습니다.
결과
  • 결제 이상 주문 건이 발생하면 즉시 탐지할 수 있을 뿐만 아니라, 모든 결제 완료 건의 이중 검증으로 신뢰성 있는 결제 시스템을 구축할 수 있었습니다.
